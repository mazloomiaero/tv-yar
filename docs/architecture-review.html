۱) محصول چیست؟

سامانهٔ مدیریت خدمات فنی و تعمیرات میدانی (Field Service Management). سناریوی اول: تعمیر تلویزیون (TV Yar)، ولی معماری باید برای لوازم خانگی، کولر، موبایل، لپ‌تاپ، تجهیزات صنعتی و نصب هم قابل استفاده باشد.

در محدوده

  • شرکت / تنظیمات / کاربران / نقش‌ها / مجوزها / شعب
  • مشتری + چند آدرس، دستگاه، نوع دستگاه، برند
  • نوع خدمت، فیلد سفارشی، وضعیت خدمت
  • درخواست خدمت، ارجاع تکنسین، گزارش، کارگاه
  • فاکتور، پرداخت آنلاین/دستی، بازخورد، اعلان

خارج از محدوده (منبع معماری)

  • چندمستأجری واقعی با tenant_id
  • انبار / موجودی / خرید
  • GPS / مسیر‌یابی / اپ Native
  • حسابداری کامل / حقوق و دستمزد
  • Work Order / Appointment / Checklist جدا
  • موتور گردش‌کار پیچیده
مدل نصب هر شرکت یک نصب Laravel + یک دیتابیس مستقل دارد. جدول company هویت همان نصب است، نه کلید چندشرکتی روی ردیف‌های کسب‌وکار.

۲) اصول معماری اجباری

  • کنترلر نازک؛ منطق کسب‌وکار در Action / Service.
  • ورودی فقط از Form Request.
  • دسترسی با Permission + Policy (نه فقط permission).
  • شماره‌های نمایشی از document_sequences با تراکنش + lockForUpdate (نه id).
  • تاریخچهٔ مالی و خدمت به‌صورت فیزیکی پاک نمی‌شود.
  • شعبه مفهوم داخلی یک شرکت است؛ branch_id همه‌جا نیست (روی ارجاع nullable است).
  • ویژگی‌های صنعت‌محور دستگاه = Custom Field، نه ستون اضافه روی devices.
  • موفقیت درگاه فقط بعد از Verify واقعی معتبر است.

۳) خط لوله درخواست

مسیرهای پنل‌ها جدا هستند: admin.php، operator.php، technical.php، accountant.php، technician.php، customer.php، به‌همراه auth.php.

۱۱) قرارداد مالی

گزارش قطعات تأییدشده← CreateInvoice← Payment← Gateway Verify / تأیید حسابدار
  • وضعیت فاکتور: pending_payment · partially_paid · paid · cancelled
  • روش پرداخت: gateway · card_transfer · cash
  • دستی‌ها با وضعیت pending_confirmation تا تأیید حسابدار
  • card_transfer نیازمند تصویر فیش؛ cash اختیاری
  • اسنپ‌شات مشتری و اقلام روی فاکتور (تغییر بعدی مشتری فاکتور قدیم را عوض نکند)
  • کارت/CVV/OTP بانکی ذخیره نمی‌شود؛ callback تکراری نباید پرداخت را دوبار اعمال کند

شماره‌گذاری

انواع سند: REQUEST (SR) · INVOICE (INV) · RECEPTION (REC) — یکتا روی document_type + year.

۱۲) وضعیت خدمت (داده، نه موتور workflow)

وضعیت‌ها در service_statuses و مجاز بودن‌شان برای هر نوع خدمت در service_type_statuses است. تغییر وضعیت تاریخچه می‌نویسد.

نمونه مسیر میدان

New → Waiting for Contact / Assignment → Assigned → Technician Confirmed → On the Way → On Site → Inspecting → Repairing → Repaired → Closed

کارگاه (همان درخواست)

Transfer to Workshop → Device Received → In Workshop → Repairing → Ready for Delivery → Delivered

وضعیت‌های کناری: Cancelled · Customer Absent · Cannot Repair · Revisit Needed · Transfer to Workshop

۱۳) ممنوعیت‌های ساختاری (برای جلوگیری از پیشنهاد اشتباه)

  • جدول ۴۲اُم اختراع نشود؛ اسامی ۴۱ جدول ثابت‌اند.
  • بدون work_orders، appointments، checklists، warehouses، stock_*، tenant_id.
  • بدون ENUM مای‌اسکیوال برای status/type.
  • بدون فرض Spatie Permission مگر قرارداد بعدی صریح و منطبق با جداول فعلی roles/permissions.
  • API REST نسخه‌دار هنوز قرارداد منبع ندارد؛ منطق باید روی Action/Service بماند.

۱۴) دستور کار عارضه‌یابی برای Claude

لطفاً این سند را به عنوان تصویر فعلی سیستم در نظر بگیر و روی موارد زیر نظر بده. پیشنهادها باید با اصول بخش ۲ و ممنوعیت‌های بخش ۱۳ سازگار باشند.

A. انسجام معماری

  1. آیا مرز Action/Service/Controller در عمل شفاف است یا نشانه‌ای از نشت منطق به کنترلر/مدل دیده می‌شود؟
  2. آیا دامنه Workshop به‌درستی «ادامه Service Request» مانده یا خطر جداشدن زیرسیستم دارد؟
  3. مدل Custom Field (دو جدول value جدا، بدون polymorphic) برای مقیاس صنعت‌های مختلف کافی است؟ جایگزین سازگار با منبع چیست؟

B. فرایند و UX عملیاتی

  1. جریان اپراتور (جستجو مشتری → دستگاه → درخواست → ارجاع) کجا اصطکاک یا گام گم‌شده دارد؟
  2. ارجاع «همیشه دستی + پیشنهاد» آیا برای ظرفیت تکنسین/شعبه کافی مدل شده؟
  3. تقویم مشتق از assignment چه محدودیت‌هایی برای زمان‌بندی واقعی ایجاد می‌کند؟

C. مالی و امنیت

  1. مسیر gateway verify + جلوگیری از double-complete را از نظر طراحی Critically بررسی کن.
  2. پرداخت دستی pending_confirmation چه ریسک عملیاتی/حسابداری دارد؟
  3. اسنپ‌شات فاکتور در برابر تغییر بعدی مشتری/قطعه کامل است؟

D. ساختار کد و مقیاس

  1. با ۶ پنل و ۴۱ جدول، کجاها احتمال تکرار Form/Controller/View زیاد است و چه abstractionای بدون خروج از معماری کمک می‌کند؟
  2. آیا جدا بودن guard مشتری + OTP/password فعلی با قرارداد منبع تنش دارد؟
  3. برای نصب‌های مستقل per-company، چه چیزهایی باید در پکیج deploy استاندارد شود (env، PHP extensions مثل iconv، document root جدا از core)؟

E. خروجی مورد انتظار از Claude

  1. ۳ تا ۷ یافتهٔ پرریسک (با شدت: Critical / High / Medium)
  2. پیشنهاد بهبود ساختاری کوتاه و اجرایی (نه بازنویسی کامل محصول)
  3. لیست چیزهایی که عمداً نباید تغییر کنند (برای حفظ سازگاری با معماری منبع)
  4. در صورت تعارض سند/کد، تعارض را صریح گزارش کن؛ حدس نزن
یادداشت وضعیت ریپو کد فعلی فراتر از اسکلت اولیه است (Actions، پنل‌ها، Form Requests، Events، Services، تست‌ها و استقرار روی app.tv-yar.com). اگر سندی قدیمی‌تر می‌گوید «هنوز پیاده نشده»، این HTML را به‌عنوان تصویر جدیدتر در نظر بگیر.
